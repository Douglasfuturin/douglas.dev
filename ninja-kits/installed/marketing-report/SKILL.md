# Marketing Report Skill

Generate a single self-contained HTML marketing intelligence report. The output is a Bloomberg-terminal-style dark-mode artifact with a headline finding, KPI tile grid, channel breakdown, content performance, and 3-6 AI-surfaced "investigator" insights with a Start / Stop / Test focus list for the upcoming period.

## When to invoke

User says:
- "Pull the weekly report" / "Monday marketing digest" / "Run the monthly recap"
- "What's working in marketing right now?"
- "Where should I focus next week?"
- "What patterns are we missing across channels?"
- Provides a date range and asks for a marketing rundown

The skill is opinionated about cadence: **weekly** (7d vs prior 7d) or **monthly** (30d vs prior 30d). Anything in between, default to weekly and note the actual window.

## Non-negotiables

1. **One HTML file out, no external assets.** The report must open identically from a Slack attachment, a saved file, or a cold email. No CDN fonts at view time (Google Fonts is embedded into the CSS), no JS, no Chart.js. Inline SVG charts only.
2. **Insights matter more than dashboards.** The investigator-style observations (3-6 of them, each with a recommended action) are the highest-leverage section. A report with great charts but weak observations has failed. See [references/analysis-framework.md](references/analysis-framework.md).
3. **Quote the data, don't fabricate it.** Every claim in an insight must trace back to a pulled metric. If a source is missing or stale, the affected insight should say so — not paper over the gap.
4. **No "Generated by AI" or "Powered by Claude" badges anywhere in the report.** The output is presented as the operator's own intelligence product.
5. **Dark mode only.** No light-mode toggle. Premium operators read this on Monday morning and don't want a white blast.

## Workflow

### Step 1 — Establish the window

Decide the period:
- `--period weekly`: last 7 days, vs prior 7 days. Default if unspecified.
- `--period monthly`: last 30 days, vs prior 30.

Resolve window start/end dates. Write them to `workspace/{slug}/window.json` so every downstream step uses the same window.

### Step 2 — Pull data from each source

For each connected source, run the corresponding pull step and write the result as a JSON file into `workspace/{slug}/data/`:

| Source | Pull method | Output file |
|--------|-------------|-------------|
| Google Analytics 4 | `python3 scripts/pull_ga4.py --start … --end …` | `data/ga4.json` |
| Meta Ads | `python3 scripts/pull_meta_ads.py --start … --end …` | `data/meta_ads.json` |
| Hyros | `python3 scripts/pull_hyros.py --start … --end …` | `data/hyros.json` |
| Metricool (social) | Call the Metricool MCP tools directly from Claude (see `scripts/pull_metricool.md`) and write the result to `data/metricool.json` |

If a source is unavailable (missing creds, API error, rate-limited), still emit a JSON file with `{"status": "missing", "reason": "…"}` and continue. The report renders cleanly with missing sources — the footer marks them as not connected, and any insights that depended on the missing source get suppressed.

See [references/data-sources.md](references/data-sources.md) for the full source registry, environment variables, and per-source schema.

### Step 3 — Compose the unified data JSON

Run `python3 scripts/compose_data.py --in data/ --out report-data.json` (built-in to the render pipeline; see [references/report-anatomy.md](references/report-anatomy.md) for the full schema). The composer:
- Merges the per-source JSONs into a single `report-data.json` shaped for the renderer
- Computes blended metrics (CAC, ROAS, MER, conv rates) by joining spend (Meta/Google) with revenue/leads (Hyros)
- Builds the 14-point sparkline arrays for each KPI tile
- Builds the heatmap grid from Metricool's hourly engagement data
- Stamps `meta.sources` with `ok` / `missing` flags so the footer reflects reality

### Step 4 — Write the analysis JSON (this is the model's job)

Claude reads `report-data.json` and writes `analysis.json`. The structure:

```json
{
  "headline": {
    "title": "One sentence with the most-important takeaway. Use <span class=\"accent\">…</span> to highlight a single number.",
    "lede": "1-3 sentence framing of WHY that headline matters.",
    "kpis": [
      {"label": "...", "value": "...", "delta_pct": 12.3}
    ]
  },
  "insights": [
    {
      "tag": "SHORT UPPERCASE TAG",
      "title": "One-sentence observation that names the pattern.",
      "body": "2-4 sentences with the evidence — quote specific numbers from report-data.json.",
      "action": "One specific, concrete next step. Not a list. Not 'consider'. A verb-led move."
    }
  ],
  "focus": {
    "start": ["3 specific moves"],
    "stop": ["1-2 things to drop"],
    "test": ["1 hypothesis to test"]
  }
}
```

The analysis layer is the high-leverage part of this skill. Detailed rubric for writing observations, picking which patterns matter, calibrating thresholds, and writing operator-voice recommendations: see [references/analysis-framework.md](references/analysis-framework.md).

### Step 5 — Render the HTML

```bash
python3 scripts/render_report.py \
  --data workspace/{slug}/report-data.json \
  --analysis workspace/{slug}/analysis.json \
  --period weekly \
  --output workspace/{slug}/report.html
```

Optional flags:
- `--brand-name "Acme Co"` — override the brand label in the top bar (defaults to whatever is in `report-data.json` meta)
- `--brand-color "#FF5C00"` — override the accent color (defaults to `#ff8c42`)

The render is fully deterministic given the JSONs. Re-running with the same inputs produces byte-identical output.

### Step 6 — Hand-off

Tell the user:
- Path to the HTML file
- Period covered + delta basis (vs prior 7d / 30d)
- Which sources came through and which were missing
- One sentence summarizing the headline finding (so they know whether to open the file urgently)

**Optional bonus**: if the user has Slack set up, post a short markdown TL;DR to a channel of their choice with a link/path to the full report.

## Cadence rituals (skill habits the operator can rely on)

The skill is built to slot into two weekly/monthly rituals:

**Monday morning weekly digest** — Pull Sunday-night data first thing Monday. Report covers the trailing Mon-Sun. Land in inbox/Slack by 9am.

**First-of-month monthly recap** — Run on the 1st (or first business day). Covers the entire calendar month just ended. Cleaner narrative than a rolling 30-day window because it aligns with how the team plans.

If the user invokes the skill mid-period ("run the report now, mid-week"), still run it — just use the rolling 7d/30d window ending today, and note that in the report header.

## Anti-patterns

These kill the credibility of the report. Never ship them:

- Insights that just restate the chart ("Traffic was up 8%") instead of explaining *why* or *what to do about it*
- More than 6 insight cards (the operator stops reading; rank ruthlessly)
- A focus list with 5+ "starts" (forces a real choice — three max)
- A headline finding that's two sentences (one sentence, with a single accent number)
- Saying "consider doing X" instead of recommending X (be definitive; the operator can override)
- Rendering charts using a CDN-loaded JS lib (the report MUST work offline)
- "Generated by Claude" footers, AI emoji, or any other LLM signals
- A "limitations" disclaimer block at the bottom — bake limitations into the relevant insight instead

## What "good" looks like

Open `examples/sample-report.html` in any browser. That's the visual benchmark. A real report should:
- Feel like a piece of intelligence product, not a marketing brochure
- Have a single sentence at the top that an operator could quote in a board update
- Surface at least one pattern the operator wouldn't have seen by skimming dashboards
- Have a focus list short enough to act on this week, not a backlog
